# 证据准入与覆盖核查：工程增量设计

## 1. 本轮交付与当前基础

本文定义下一轮 CLI 增量，当前状态为设计完成待实施。接口、字段和命令示例均是拟议协议，不表示代码已经支持。

本轮目标是让每条现行知识的准入依据，以及一批未处理的原文候选声明可检查。先验证机制是否改善质量和成本，再决定是否默认启用。

本设计沿用已选定的证据与覆盖核查方向。具体采用独立开关，是本轮的工程取舍。

| 实现方式 | 收益与代价 | 本轮选择 |
|---|---|---|
| 只增加提示词要求 | 改动少，但无法程序检查处置是否缺项、来源是否错配 | 不采用 |
| 在现有两步 verified 中增加结构化审计 | 复用调用，单独测量收益；协议和本地报告更复杂 | 采用，先主动开启 |
| 每条知识另加模型判定或多轮投票 | 可增加判定机会，但调用和费用随条目增长 | 留待独立消融，不作默认路径 |

| 能力 | 当前基础 | 本轮增量 |
|---|---|---|
| 整需求按序输入 | 已有 requirement 命令 | 复用 |
| 需求内新增、更新、失效、合并 | 已有事件重放、历史和来源关系 | 复用 |
| 理由、边界的字段复核 | d9cdd76 已实现结构化复核 | 复用，不把模型判定称为程序语义证明 |
| 明确理由未知的处理 | 已有原文声明清单 | 复用声明定位与处置经验 |
| 角色与确认依据准入 | 来源有角色，尚无独立准入协议 | 新增当前知识的准入凭据 |
| 原文候选遗漏核查 | 尚未实现 | 新增候选清单和逐项处置 |
| 字符位置与溯源 | 已有文件、行、消息和逐字引文 | 程序计算行内字符区间，生成本地只读报告 |

本轮保留阶段接口、原始预测、gold 和 Mario 原评分。不引入跨需求数据库、向量检索、多轮投票或新的外部依赖。跨需求共享记忆作为下一轮独立交付。

## 2. 处理流程与责任

```text
完整需求的有序节点
  → 程序建立来源、角色、声明候选与字符位置索引
  → 第一次模型调用提出候选事件
  → 第二次模型调用修订事件，并逐项给出字段复核、准入和候选处置
  → 程序重放事件，校验全部关联、来源、顺序和清单完整性
  → 保存当前知识、历史及审计报告；需要复核时单独保留草稿
```

模型判断一段话是否确认了某个提议、引文是否支持业务含义、两条规则是否相同。代码检查来源是否存在、角色是否符合所称依据、确认是否晚于提议、支持链接是否真实，以及应处理的候选是否遗漏。

用户发言不自动成为最终决定，产物也不自动永久有效。后续节点可以替换或取消早期产物。准入检查必须绑定最终重放后的当前知识。

## 3. 范围、模式与兼容

首版增加主动开启的 `--evidence-audit v1`，仅用于 `requirement extract --mode verified`。未传该参数时沿用当前 schema 2 行为，包括已有字段复核。阶段命令、compare、battle 和 series 首版不接入这个开关。

拟议命令如下，实施完成前不能直接运行：

```bash
python3 -m decision_memory requirement extract \
  --manifest examples/requirement-cache/manifest.json \
  --config config.local.toml --mode verified --evidence-audit v1 \
  --output runs/evidence-audit-pilot/result.json
```

审计开关与 baseline、artifact-only 同用时，在模型请求前报参数错误。验证新结果仍使用既有 `requirement validate --manifest ... --result ...`，不新增模型请求。

正常调用数保持两次。每步完整 JSON 中的协议结构错误仍最多修复一次，总模型调用最多四次。结构有效的语义待确认直接保留待复核状态；混合错误的优先级见第 8 节。

## 4. 来源和字符区间

继续使用 `Sample.catalog`、`RequirementSample`、原文文件哈希及节点顺序。准入使用实际索引中的 user、agent、artifact 或未知角色，不信任模型自报角色。

首版不修改已有来源解析规则。角色未识别时保留未知；不能为了通过审计改为 user。若有其他明确用户或产物依据，可据此准入；只有未知角色来源且无法确认的知识进入待复核。

新建 `evidence_spans.py`，由代码把引文解析为 `source_id + start + end`。坐标是原始索引行 `Source.text` 内、从 0 开始的 Unicode 码点半开区间，满足 `text[start:end] == quote`。它不是 UTF-8 字节位置，也不是浏览器 UTF-16 位置。

区间旁保存行文本摘要和原始文件摘要。沿用当前 BOM 和换行索引方式，不做 NFC、去空格或标点改写。报告展示索引行；不能把行内区间声称为原始文件的字节偏移。

同一引文在一行出现多次时，不选择第一个。模型须扩大引文至唯一连续片段；仍不唯一则按结构错误处理。旧结果不自动补字符区间。

为区分引文的业务焦点和消歧上下文，允许 `evidence_focus` 声明例外。每条例外用 knowledge_key、field、source_id 和完整 quote 精确关联当前证据，并提供 focus_quote。focus_quote 必须是完整引文内唯一的非空连续片段；代码据此计算焦点区间。没有例外时，焦点就是完整引文。

若扩大后的引文同时包含业务规则和排期，复核者可把焦点限定到业务规则。候选关联和排除冲突用焦点区间，不把为了消歧保留的其他上下文自动当成现行知识。例外不能改变原始引文、来源或字段正文。

## 5. 当前知识的准入规则

每个当前 `knowledge_key` 必须有且仅有一个准入记录。所有准入锚点必须出现在该当前条目的 conclusion.evidence 中，由修订后的事件产生；代码不静默给条目补证据。

| 路径 | 必要依据 | 程序检查 |
|---|---|---|
| user_direct | 用户直接表达当前规则 | 至少一个实际 user 来源，引用与当前结论关联 |
| artifact_direct | 产物直接表达规则 | 至少一个实际 artifact 来源；现行状态仍由最终事件和语义复核决定 |
| confirmed_proposal | Agent 提议及用户确认 | Agent 提议与 user 确认均有逐字依据；确认晚于提议；模型说明二者确认关系 |
| needs_review | 依据不足或确认关系不清 | 不作为审计通过的现行知识发布 |

用户只说“对”时不能把它当完整规则的直接证据。采用 confirmed_proposal，保留完整提议和确认。若一句“对”对应多个提议，模型必须说明确认范围；无法判断则待复核。

当前理由或边界明确归因于“用户要求”“需求方要求”“用户指定”时，另列用户归因检查，要求该字段引用实际 user 来源。首版用版本化的保守措辞规则识别这些显式归因，报告识别范围；不承诺发现所有隐含归因。

程序只证明角色、链接和先后符合协议。用户原话本身是否支持该规则、确认是否真正指向该提议，仍是模型判定及独立抽查的对象。不能用不相关的用户话语充当确认。

不在代码中删除未通过条目后假装事件重放成功。复核模型应修订候选事件，或把尚未确认的提议放入未决项。无法形成可靠结果时，输出待复核草稿，不自动回退为旧规则有效。

## 6. 候选覆盖核查

### 6.1 首版候选范围

候选来自原始材料，不来自 gold，也不由提取结果反推。程序建立下列清单：

- 产物中的非空内容片段。仅跳过纯结构标记及固定通用章节标题；包含业务断言的标题仍保留。
- 用户或未知角色对话中含显式约束、范围、口径、否定、修改或未决标记的片段。首版标记集包含“必须、仅、最多、不超过、禁止、不做、改为、改成、保持、替代、取消、不再、口径、是指、待确认、未说明”。
- Agent 提议不因命中标记自动成为应沉淀知识。当前结论引用的提议由准入检查处理。

句号、分号等标点用于产生可定位片段，保留原始字符。数据表、代码块里的正文不整块删除，是否可复用由复核者说明。同一行的不同声明使用不同 unit_id 和区间。

片段只是核查单位，不是自动认定的原子知识。条件、否定和后续回复仍放在完整上下文中理解。混合单位允许关联多个目标；无法说明全部相关内容的处置时标为 needs_review。

候选策略及标记集合有独立版本和摘要。首版上限为 256 个候选单位；超过上限明确报错，不截取前 256 个，也不自动关闭审计。该限制只作用于主动开启的 v1。

首版无法保证找到所有隐性约束、未命中标记的对话决定或全部混合句事实。报告中的“候选处置完整”仅表示清单完整，不能替代以固定参考计算的召回率。

### 6.2 每个候选的处置

| 处置 | 必须关联的目标 |
|---|---|
| current | 当前知识的 conclusion、reason 或 boundary 字段，可多个目标共同支持 |
| history | 实际的旧版本、替换或失效事件及对应来源，不能只写“已经过期” |
| pending | 最终未决项，或已校验的理由未知声明及其当前 reason |
| non_reusable | 固定排除原因，如排期、格式、纯接线、闲聊，并说明原文依据 |
| needs_review | 明确说明尚不能决定的内容，不计为已覆盖或无需提取 |

每个 unit_id 必须出现且只出现一次。关联目标存在、状态正确且确实引用该片段。链接按字符区间核对，不按整行 source_id 粗略关联，避免同一行中的独立业务事实与排期互相污染。

current 目标必须已通过准入和字段复核。理由正文为“未说明”且证据为空时，通过现有 reason_checks 的声明关联，不能把未知原因补成结论。

non_reusable 不能把当前知识实际依赖的同一片段排除。只因同一行的另一个片段被引用，不构成冲突。混合声明的多个事实是否都处理，仍需语义复核；程序不把“存在某条引用”当成完整覆盖。

### 6.3 区间关联的明确语义

代码按同一来源中的半开区间求交。交集包含至少一个非空白、非纯标点字符，才属于位置相关；它不要求引用完整包含整个候选。多个真实目标可以共同关联一个候选，不能用同一句引用反复增加覆盖计数。

例如候选是“必须限制为 100 条”，证据只引“100 条”，位置检查可以通过，但不能据此自动判为完整支持。模型须核对对象、限制关系和数值，报告 semantic_coverage。current、history、pending 只有 full 才算该候选处置完成；partial、unclear 转为 needs_review。non_reusable 使用 not_applicable，并保留排除原因。

判定 non_reusable 是否冲突时，检查全部当前条目证据的焦点区间，而非仅检查本行主动列出的目标。排期与业务规则位于不同片段时允许分别处置。扩大引用跨过排期时，先声明真实的业务焦点，或收窄引文。

这些是定位和协议规则，不是自然语言完整性的程序证明。模型把语义不完整的引用错误判为 full，仍需要独立评测发现。

## 7. 审计协议和结果文件

保持 `items`、`events`、`history` 和 `grounding_review` 的已有语义。开启 v1 的新结果使用 schema 3，增加 `evidence_audit`；未开启仍生成 schema 2。旧 schema 1、2 保持原样离线可读。

第二次模型回复新增 admission_checks、user_attribution_checks 和 coverage_checks。unit_catalog 与最终字符区间由程序生成，模型不能修改。代码校验后将两者一起保存到 evidence_audit。

```json
{
  "policy": "evidence-v1",
  "evidence_focus": [],
  "admission_checks": [
    {
      "knowledge_key": "detail-cache-refresh",
      "basis": "confirmed_proposal",
      "direct": [],
      "proposal": [{"source_id": "D.design.00003", "quote": "建议按变更事件刷新商品详情缓存"}],
      "confirmation": [{"source_id": "D.design.00005", "quote": "就按这个方案"}],
      "notes": "此确认指向前一条完整提议，范围仅为商品详情缓存。"
    }
  ],
  "user_attribution_checks": [],
  "coverage_checks": [
    {
      "unit_id": "U001",
      "disposition": "current",
      "semantic_coverage": "full",
      "targets": [{"type": "item_field", "knowledge_key": "detail-cache-refresh", "field": "conclusion", "evidence": {"source_id": "D.design.00003", "quote": "建议按变更事件刷新商品详情缓存"}}],
      "notes": "当前结论覆盖该刷新规则，范围限定在另一字段共同表达。"
    }
  ]
}
```

这是一个局部示例，完整回复必须覆盖实际清单。direct、proposal、confirmation 三个数组均须存在。user_direct、artifact_direct 使用 direct 锚点，另两个数组为空；confirmed_proposal 的 direct 为空。needs_review 不声称准入成功，三个数组可保留实际候选依据。所有锚点仍须是该当前结论的真实引用。

目标类型固定为 item_field、history_event、open_question、reason_check。每个目标都带 evidence 的 source_id 和 quote，必须属于目标实际保存的证据。历史目标用实际 event_id 及对应字段路径；问题使用最终数组顺序派生的 Q001 等编号，不写回原始问题。

reason_check 目标以 source_id 和完整未知声明片段联合定位。覆盖关联使用该检查记录中已经校验的 evidence，允许其当前 reason 为“未说明”且 evidence 为空。代码核对 retained 状态及当前 knowledge_key，不把声明存在当成原因已知。

审计摘要绑定输入文件、节点顺序、来源角色、策略版本、当前知识、memory_index、history、open_questions 和 grounding_review。离线 validate 从原始输入重建 catalog、候选及区间，再重放全部链接检查。仅重算外层文件摘要，不能绕过内部摘要和关联检查。摘要用于发现不一致，不提供结果签名，也不能识别所有语义一致的重写。

结果旁生成只读 `result.audit.html`，展示当前知识、来源片段、历史和未决处置。HTML 使用程序算出的区间高亮，转义全部原文，不加载外部脚本，也不包含身份凭证。

## 8. 失败、调用记录和成本

### 8.1 校验顺序

格式错误、缺项、重复、无效角色或错误链接优先按结构错误处理。先完成 JSON、来源和链接校验，再解释 needs_review。混合回复中即使有一条 needs_review，其他缺项或错误链接仍最多触发一次仅修复结构的调用；修复提示须保留已有待复核标记，不能要求模型补造业务结论。

若结构修复仍失败，保存为结构无效草稿，不称为完整待复核结果。结构有效且存在 needs_review 时，用独立的待复核异常结束，不再追加格式或语义重试。CLI 保持非零退出码 2，记录 audit_status=needs_review，不生成成功的 result.json。

证据不足却仍输出当前知识，需要模型修订事件，不由程序猜测正确业务规则。程序不得因为审计未通过就静默删除条目、恢复旧决定，或把部分结果标成通过。

### 8.2 接口传输策略

开启 v1 时，运行时的有效模型配置强制 retries=0，不修改用户的 TOML 文件。记录请求配置摘要、实际生效配置及 transport_policy=no-auto-http-retry。既有模式的客户端行为保持原样。

超时、连接断开、流式响应未完成等执行结果不确定的错误立即记为 unknown 并停止。所有 HTTP 错误，包括 408、429 和 5xx，首版也不自动重试。已收到错误回执记为接口失败，并单列用量是否可确认；不能仅根据状态码推断没有计费。

仅在完整接收并解析出有效 JSON 后，才允许对协议结构错误作一次修复。截断、拒绝、无效 JSON 或不完整响应不进入这条修复路径。因此，正常两个模型请求，最多发起四次；任一步结果不确定就停止，不存在隐藏的 HTTP 倍增重试。

这个选择会降低临时网络故障时的自动恢复率，但能避免未知付费请求的重复执行。是否增加有明确回执的限流重试，留待后续单独评估。

### 8.3 回执和预算

审计模式在请求前预留 `result.run/`，原子记录输入、实现和配置摘要，以及每一步 started/completed/failed 状态。模型响应收到后先保存该步 JSON，再校验。记录不包含 API Key、请求头或环境变量值。

进程中断而没有完成回执的步骤标为 unknown。已有 run 目录时普通 extract 拒绝重跑。本轮不增加自动续跑；检查点用于保留已完成阶段与定位故障。没有完成记录不能当成没有发生费用。

真实验证按单个需求使用独立后台进程，立即返回进程号和日志路径。工具连接的生命周期不承担批次执行生命周期，不再把多个长模型任务绑定到一次工具等待。整个过程不打开 IDE 终端或操作键鼠。

保存指标包括逻辑模型调用、HTTP 尝试、输入和输出 token、累计模型耗时、调用总墙钟时间、候选数量、待复核数及可用费用。失败或未知调用用量缺失时保持未知，不能记为零。

不得在第二轮重复嵌入两份完整材料。审计仅增加必要候选片段和关联字段。静态清单超限在第一次调用前失败；第二步动态请求超长时保存第一步记录并报错，不截断原文，不暗中降级。

## 9. 本地真实会话的使用

用户提供的本地 Codex 历史会话可作为真实输入来源。当前仅纳入数据准备方案，不全量读取正文，也不训练模型。

会话 ID 不等于需求 ID。先按项目和完整业务任务归组，一个需求的全部会话、节点和变更保持在同一组。选择已结束且有最终文档或明确代码版本的需求；材料不完整时标记缺项，不补造产物。

保留真实用户与助手的业务讨论。系统、开发者指令、内部调度和工具元数据不混入业务对话；助手的业务提议不能整体删掉，否则会丢失纠偏过程。工具产生的文件与代码版本单独作为产物来源核对。

适配器先核对本机实际格式，使用原始角色字段生成既有 Markdown 与 manifest，不把截图中的数据库表名当成公开稳定接口。原始 JSONL 或压缩文件只读，保留会话 ID、记录位置和内容摘要的本地追溯关系。

原会话留本地。若含密钥或敏感信息，以脱敏副本作为实际评测输入，引用必须匹配该副本，并标明它是脱敏快照。保留副本摘要和本地原记录关联，不能把改写引文称为原文逐字证据。原始记录、映射及内部产物不上传公开 GitHub。

建议先选 3 个材料完整的真实需求试点。候选参考可以先起草，再由了解业务的人核对结论、理由、范围与来源。会话和代码实现均不天然等于正确答案。

现有六例归入开发回归集。新数据按完整需求划分开发与留出验收，同一需求的不同会话不能分到两边。对留出样本调过代码后，重新归为开发集，不能继续声称它未参与调试。

## 11. 验收与实施边界

| 用例 | 应有行为 |
|---|---|
| 只有 Agent 提议 | 不能以当前知识通过准入；可转待确认 |
| 完整 Agent 提议后用户说“对” | 保存提议与确认关联；不要求用户重说完整规则 |
| 拿无关用户话语凑确认 | 结构检查定位关联，语义复核及人工样例判为不支持 |
| 理由自称用户要求却只引 Agent | 拒绝该归因 |
| 旧产物被后续节点取消 | 只保留历史，不认定产物永久有效 |
| 条件范围、业务口径候选被遗漏 | 暴露未处置单位，不能冒充清单已完成 |
| 同一行有业务规则和排期 | 分片核查，允许不同处置，不按整行互相污染 |
| 相同行内有两个相同短引文 | 扩大引文至唯一；不默取首个位置 |
| 中文、emoji、CRLF、BOM | 区间可重建匹配，不混淆字节和码点 |
| 历史、未知、未决目标错配 | 拒绝链接；未知不升级为现行结论 |
| 缺项、重复、伪造处置或重排问题 | 保存后重放仍能发现 |
| 只引用“100 条” | 位置相关不等于语义完整，需模型核对限制关系 |
| 扩大引用跨过业务与排期 | 使用真实焦点核对，允许排期独立排除 |
| needs_review 与缺项混合 | 先一次结构修复；结构有效后才结束为待复核 |
| 超时、断流、HTTP 错误 | v1 无接口自动重试，状态和用量按实记录 |
| 超预算或使用不支持模式 | 请求前报错；动态超限保留已付费步骤记录 |
| 第二步中断 | 已完成第一步可查，第二步为 unknown，不自动重发 |
| 旧 schema 1、2 | 原样读取，不追认新审计通过 |

程序测试覆盖确定性规则和完整 CLI 的本机 HTTP 行为。真实模型用固定输入和参考另行评审。报告分别给出知识准确率、引用支持、完整参考覆盖、错误准入、候选处置完整度、拒绝率及成本。

先比较相同需求、相同模型配置下的当前 verified 与 verified＋审计。再与 artifact-only、baseline 做原有消融。质量按固定参考计，不以候选清单或程序测试数量代替质量。小样本结果只作为试点信号。

实施分为字符定位与准入、候选核查、报告及真实试点三个可验收增量。只有通过原有回归、角色与多事实样例，以及成本对照后，才讨论默认启用。完成本轮后再设计跨需求共享记忆。
