# 整需求的 Mario 出题与对照评测

## 目标和授权

用户已确认继续：使用现有两位 Mario 员工，在原测试群展示出题和评审，准备 6 个新需求，对比逐节点提取与整需求提取。沿用后台执行、禁止操作键鼠和远控、保留所有旧记录的约束。此前的解释与用户“好的，那你做吧”构成本轮工作范围的确认；具体实现选择由本轮记录，不再次请求相同授权。

先检查当前员工是否能实际接单。Mario 工具可发现不代表员工执行成功。最小健康检查创建独立结果文档，向两位现有员工各发一次指令，要求独立写回标记并在原群展示。请求开始前保存状态；未知结果不重发。当前公开工具无法编辑员工发布配置时，如实保留阻塞证据，继续完成可离线验证的工程工作。

## 实现选择

选择扩展现有 Battle 和 Series 状态机，复用 Docs 回读、任务摘要、防重发和冻结校验。另建整套协调器会重复这些保护；只拼接旧样本不能测试后续节点推翻旧决定。保留原阶段协议和评分，新增 `stage=requirement`。

以独立模块负责整需求回传与比较，避免继续把协议和推断逻辑堆入协调器。运行时仍为 Python 3.11+ 标准库，源代码通过 apply_patch 修改。沿用现有分支以保持本机 Weaver 归属。

## 题目与参考

整需求出题回传 result.json、requirement.json 和 gold.json。requirement.json 包含 schema_version=1、requirement_id 及有序 nodes；节点含 id、stage、dialogue、artifact，后两项是原始正文。协调器把正文保存到独立节点文件，再生成普通需求清单。

gold.json 每条含 id、text、kind（decision 或 uncertainty）和非空 evidence。证据含 node_id、source（dialogue/artifact）及同一行的原文 quote。decision 是最终有效知识，uncertainty 是仍未知的字段或未决事项。参考不得混入原始材料。代码核对来源位置，真实评审员工核对语义；必要时退回出题人，最多 3 轮。

原始材料最多 64 节点、每份 2 MB、总量 8 MB。整需求业务事实和技术约束同样重要。gold、brief 和审题反馈都不传入提取器。

## 批次先冻结再作答

整需求 Series 分 prepare/evaluate 两遍。prepare 只让现有员工出题和审题，逐例停在冻结后的 awaiting_model。全部 6 例完成后，写入整批冻结清单，绑定每例输入和参考摘要，再进入 evaluate。批次中不修改提示词、算法或参考答案。

争议样本保留 human_review，单独列出，不替换为协调器自编题。远端调用结果未知、协议错误或发送失败时保留状态并停止。旧阶段批次继续原来的单遍行为。

## 同一材料的两个方法

新增 `requirement compare`，只读取原始材料，输出一个比较包和各方法的原始结果：

- whole：现有需求级提取器，使用批次 mode。
- per_node：旧阶段提取算法分别读取各节点，固定 baseline，然后机械拼接。只重编条目 ID 和来源编号，不删除重复、未决项或过期决定，不改结论、理由和边界。

逐节点算法可以接受需求读取器产生的节点样本；现有单阶段 CLI 的阶段枚举不扩大。比较报告说明算法入口与现有阶段 CLI 的区别。两个方法使用同一模型配置，分别保留调用、重试、耗时、token 和费用。未配置单价时费用为空。

比较包绑定输入摘要、公开配置、提示词、原始预测文件摘要和机械映射。离线重算逐节点拼接，拒绝篡改。原始结果已有时不能重新付费覆盖；失败或未知的调用不自动重试，显式新尝试留在新目录并保留旧错误。

## 评分

两种方法使用随机但持久的 A/B 标签，评分任务不包含方法名或模型模式，只含原文、固定参考、分类策略及原始预测的评分视图。标签隐藏用于减少方法名带来的偏好，不声称评分模型具有完全独立性。

复用 v2 评测：judgments、open_question_judgments 和 reference_judgments。有效知识与未知信息分别判断 full/partial/absent/null。只有正确且引用支持的原始输出才能支持参考，主覆盖率仅计 full，未审不算通过。评审只返回判定，不改预测或参考。

整个评分任务的 prediction_digest 绑定比较包；每个评测表单独绑定对应原始视图。人工确认保持 pending，正式成绩为空。旧 v1 员工评分不迁移。

## 验收与实际限制

补充真实本机 HTTP、CLI 子进程和离线员工 fixture 测试，覆盖多轮修订、整批先冻结、参考隔离、旧输入校验、原始预测不可修改、机械拼接、A/B 回传与恢复防重发。fixture 只证明程序行为。

为 6 个未用过的场景固定 brief，覆盖业务口径改变、职责归属、同范围修订、不同范围共存、旧产物失效和未确认事项。首批只运行冻结后的代码版本，不用评分反馈调整同批题目。

真实群任务仅在最小健康检查和模型、Docs 预检通过后启动。若平台配置或身份阻塞，保存证据和可直接恢复的批次，不伪造员工回传，不启用远控，不用当前聊天替员工编题。

## 设计检查后的明确约定

独立设计检查没有发现需要用户补充的决定。争议题采用严格门槛，6 例全部通过和冻结前不提取。未知信息按整个需求结束时的状态判断；早期已解决的问题不算最终 uncertainty。整需求参考使用指定节点的逐字引文，不沿用跨文件的宽松搜索。

批次冻结还绑定参考分类策略、提取 mode、公开模型配置、提示词和实现文件摘要。直接恢复单个 Battle 也必须核对整批门槛。比较包绑定原始预测摘要、评分视图摘要和机械映射，v2 表仍绑定各自视图摘要。分类策略由审题通过的 gold.kind 确定性生成，提取前冻结。
