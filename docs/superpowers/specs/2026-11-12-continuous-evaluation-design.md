# 连续生成与评测设计

状态：用户已选择“先跑 6 个，跑完汇总”，按此方案实施。

## 要解决的问题

当前 battle 只负责一个 case：出题、审题、返修、提取和评分。达到等待时限或遇到阻塞后，命令会退出。代码没有创建下一个 case 的外层循环。

MyFlicker 的编码会话也不是调度服务。它回复完成后，不会因为配置文件更新而自动发起新任务。上一次有效的 WQ_API_KEY 只在当次后台进程中存在，新进程没有继承该凭证。

用户需要启动一次后，程序连续生成和评测 case，结果写到 KIM 与本地。聊天会话结束不应中断已启动的批次。所有操作在后台完成，不操作键盘鼠标，不开启远程控制。

## 实现方式

新增独立的 Python 后台批次进程，复用现有 Battle。它按清单串行处理 6 个新 case，完成一个后自动开始下一个，跑完生成汇总。

批次中的每次派发采用独立的派发助手上下文，保存对应 threadId 和消息回执。真实出题、审题和评分员工仍是原来的两位，每次接收完整的当前任务材料。原有单 case 模式默认的共享派发线程保持兼容。

其他方式的取舍：

- 让 MyFlicker 聊天会话反复执行命令：依赖会话继续运行，不适合作为长期调度器。
- 安装开机自启服务：会增加启动、凭证和维护范围，本次不需要。
- 独立后台批次进程：聊天结束后仍运行，有明确的 case 数量、进度和停止入口，适合当前验证任务。

## 每个 case 的流程

1. 从批次清单取出场景要求，创建独立任务编号和输出目录。
2. 真实调用现有 Mario 出题员工，生成 dialogue、artifact 和候选 gold。
3. 真实调用现有评审员工审题；需要返修则回到出题人，每个 case 最多 3 轮。
4. 审题通过后固定输入和参考，只把 dialogue、artifact 交给 decision-memory 提取。
5. 保存原始预测，再调用真实评审员工评分，保存回传和本地汇总。
6. 记录该 case 的结果，自动开始清单中的下一个 case。

S003 已完成，保持原样。本批次使用新目录和新编号。现有 v1 评分与旁路 v2 评测保持各自版本，不在已完成数据上改分。

## 启动与凭证

启动前检查模型配置、当前进程的密钥、Mario MCP 和文档读取能力。模型入口做一次最小连通性请求。检查未通过时，不创建出题文档、不发送群消息。

密钥只通过启动进程的环境变量传入。后台批次与其提取子进程继承该环境，整批共用，密钥不进入命令行参数、日志或项目文件。程序退出后再次启动或恢复，仍需向新进程提供环境变量。

提供启动、查看状态、请求停止和断点恢复入口。状态显示批次 PID、当前 case、当前阶段、已结束数量、阻塞原因和结果路径。不会把聊天会话的 completed 当作批次完成。

## 停止与恢复

达到配置的 case 数量、用户请求停止或遇到无法继续的外部条件时，保存进度并退出。进程恢复时先收取已有回传，不重发已知或未知发送，不重跑已完成 case。

文档读取等临时故障在现有等待时限内继续核对。缺少凭证、401、402、未知创建或未知发送会标明阻塞原因，不通过反复付费调用或重复群消息尝试恢复。审题超出 3 轮的 case 保留待人工状态，不伪装为通过。

首批连续运行是有限批次，不安装开机任务。若用户选择长期运行，仍需要明确停止条件和资源上限后再启动。

## 验证

- 用现有受控 HTTP 与员工 fixture 验证：case A 完成后自动进入 B；恢复不会重复 A 的模型调用或派发。
- 缺少密钥时，在任何远端写操作前失败。
- 停止、超时和发送结果未知都保留可恢复状态。
- 原始预测、固定参考、员工回传始终可追溯，参考答案不进入提取输入。
- 实跑新批次，确认至少一个新 case 完成后自动开始下一个，并取得真实派发回执及员工文档。

该批次用于生产测试样本和测量提取效果，不会自动训练模型或自动改写 CLI 代码。模型与规则的改进应以评测结果为依据，另做可验证的修改。
