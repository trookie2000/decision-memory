## 先区分两类验证

合成批次用来检查整个流程能否执行：出题、审题、返修、固定材料、独立提取、评分和汇总。真实结果保存在 `runs/continuous-six-20261112/`。自动测试用来检查程序行为，不计入模型成绩。

官方样本用来判断提取是否符合题目要求。附件有两个需求，每个需求包含需求分析和技术设计，共四份阶段输入。每次只给模型当前阶段的对话和产物，不能附带参考答案、评审意见或下一阶段材料。

## 建议执行顺序

官方四阶段 baseline 已完成，现有原始输出继续保留。新的独立测试可按下面命令执行；先确认终端已设置模型配置要求的环境变量。对耗时较长的兼容网关，可按官方样本记录启用流式接收和接口支持的推理强度。

```bash
.venv/bin/decision-memory batch \
  --dataset data/public-samples.zip \
  --config config.local.toml \
  --mode baseline \
  --output runs/official-baseline
```

批处理汇总会记录成功、失败和用量。失败后保留原文件，修正实际错误，再对同一目录使用 `--resume`。不要为了得到高分改写原预测或参考。

随后逐条核对预测。重点检查已否决的旧方案有没有混入最终结论，未知理由有没有编造，本期范围有没有扩大，以及结论、理由和边界各自的引文是否充分。评测命令见 [评测口径](evaluation-protocol.md)。

发现具体错误后，再用相同模型和输入运行另外两个模式。比较新增调用是否改善这些错误，同时记录耗时和用量。完成这一轮测量后，才有依据决定是否修改提示词或提取流程；训练模型目前不在必要步骤中。

## 如何解读现有分数

`battle` 当前沿用 v1：只给 `items` 接收结构化判定，`open_questions` 不在其计分分母中。参考 ID 关联也不能说明复合参考已完整覆盖。不要将 v1 的匹配比例写成官方识别质量，或直接解释为模型遗漏比例。

参考集、原始预测和已保存判定保持原样。若补 v2 复核，使用新文件，并标明是事后口径整理还是新的评测。比赛是否达标，以官方计分和实际人工复核为准。
