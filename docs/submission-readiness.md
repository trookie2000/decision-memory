## 质量门槛

用户提供的题面要求：识别质量至少 70%、条目准确率至少 85%、随机十条来源至少八条可核查。三项均达到后，才进入方案创新性、工程合理性和可落地性的比较。

最新完整需求的三个数字为24/32（75%）、24/26（92.31%）和10/10；全部条目的引用支持为22/26，说明一次十条抽样不能代表所有引文都充分。固定正文的成对对照为23/32→24/32，准确率不变。早先单独判卷为22/32，两次判卷的差异单列，不能把全部变化归功于程序。

第一轮28/32、22/22、9/10及中间未达标的输出都保留，不挑最高分作为最新版。最新阶段诊断也未证明过门槛；另一份解释材料的严格覆盖2/10、准确7/12、来源抽查2/10。它已用于诊断，归入开发材料。下一轮质量工作应修复已知理由误写“未说明”、必要条件被扩为充分条件、提案被写成完成态，再用新的未见材料验证。

单阶段只用本阶段材料，不能偷读未来节点。附件的关键词阶段投影存在复合条款与分配不明问题，37 个投影位置仅作诊断。完整需求、单阶段和设计草案迁移检查分别报告，不更换有利分母。

新材料失败、协议修复和不充分证据都要保留。未发布的答案不伪装成高准确率，也不作为零分结果混进语义分母；可用率单独列出。原 Mario 判定保留，新的 Codex 独立判卷不冒称 Mario 或人工确认。

## 评委怎么运行

```bash
python3 -m decision_memory run \
  --dataset /absolute/path/public-samples.zip \
  --scope stage \
  --config config.local.toml \
  --output runs/judge-001
```

完整有序需求使用 `--scope requirement`，自定义材料使用 `--manifest`。运行范围由实际给定输入决定。配置、预算和错误处理见 [评委本地运行](judge-run.md)。

一次运行生成结构化 JSON、知识 Markdown、可点击原文的 HTML 和批次报告。HTML 可以打印为 PDF。模型调用与报告生成分开，导出报告不增加模型调用。运行报告不读取标注，也不自动给自己判准确率。

本地 MyToken 模板已验证自定义鉴权头和脱敏；真实 MyToken 入口与积分尚未单独实测。已获准的另一网关完成真实 CLI 调用。评委需使用自己的获准配置与凭证。

## 后续优先级

1. 先补正式评测口径：取得出题方对阶段参考和复合条款的分配，使用对应输入重新验收，保留未达标及发布失败项。
2. 继续质量改进：当前两个完整需求只是小样本过线。固定模型与预算，验证更强的获准模型或通用语义检查；新的未见需求须包含理由变更、条件和最终状态。已揭晓材料不再作盲测。
3. 在评委的真实 MyToken 环境跑一例，核对入口、可用模型、积分与异常回执。模板测试不能代替这一步。
4. 复用现有 `run` 和报告，最后按正式要求提交方案、代码包、实验报告、复现及 AI 说明。无需为展示先搭网站；若明确要求在线服务或在线 Docs，再补对应适配。

前三项会影响正式质量和现场运行，排在报告外观、Word 导出及其他展示功能之前。当前自动报告已经解决“运行后得到可读文档”，不再另起一套报告系统。

## 同事如何接续

先取得已提交的代码或最终源码包，按 README 检查离线样例，再用自己的模型配置运行一个新输出目录。不要把业务原文、固定标注、完整运行输出或凭证上传公开仓库。代码、通用配置、虚构样例和汇总文档可以提交。

两个 Codex 窗口可分别负责实现和独立评测。开发窗口只看输入、实现与输出；评测窗口读取固定输入、参考和匿名答案，核对最终状态、理由、边界及自身引用。两个窗口使用各自目录，代码并行修改时使用独立 worktree，避免共享分支状态。

每轮先固定版本、输入和参考，再预测、判卷、保留错例、修复通用机制并重新测试。出题和评审结果用于检验及改进程序，不会自动训练模型权重。已用于修复的新材料转为开发集，下次泛化验证另用未见材料。
