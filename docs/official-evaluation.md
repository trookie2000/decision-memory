## 修正了什么

最初沿用原非流式配置，首阶段三次 HTTP 尝试均未取得完整响应。最小调用能返回 HTTP 200。相同材料的流式诊断持续约 354 秒，最终返回 length：12,000 个输出 tokens 中有 9,995 个推理 tokens，正文被截断。这份诊断没有用于计分。

客户端现支持可选流式接收和 reasoning_effort。新一轮统一使用 stream=true、reasoning_effort=low、timeout=600、retries=0；模型、输入和提取提示词保持一致。原 config.local.toml 与历史六例没有修改。参数的接口差异见 [Moonshot 官方校验项目](https://github.com/MoonshotAI/Kimi-Vendor-Verifier/blob/main/tests/k3_features/test_thinking_effort.py)。

流式客户端收齐结束状态后才保存结果。中断、过滤、工具调用和截断不能成为成功输出。新增测试先重现失败，再修正实现；独立代码复核提出的总超时和 EOF 重试问题也已按此方式处理。完整 123 项测试通过，旧六例的 310 份受保护文件仍能通过审计。

## 正在核查的质量

官方材料已经提供题目。本轮由 CLI 独立提取，现有 Mario 评审员工检查原始输出，不再生成新的合成试题。

拍卖热度需求分析有预测前固定的 11 条参考，区分八个决策检查点和三个未知检查点。其他三个阶段先核查逐条正确性、引用与未决信息，尚无可报告的参考覆盖率。官方总标注跨阶段组织，不能直接拿下一阶段的信息判当前阶段遗漏。

评分侧实际拦住两类问题：一份回传把未知参考指向生效结论字段，v2 校验拒绝计分，已请求原评审员工修正；另一份任务文档回读出现字符差异，校验在发送前停止，随后用标准 JSON Unicode 转义传递同一输入并再次核对原值。初稿、失败回执和修复记录分别保留，没有由主会话替员工补判定。

初评与待回传状态以本机 `runs/official-evaluation-20261113-stream-low/evaluation-summary.md` 和 `grading-summary.json` 为准。人工确认与比赛正式成绩保持为空。KIM 群回复尚未独立回读，本次只读查询返回业务鉴权 HTTP 401；发送回执和员工 Docs 回传分别记录。

## 下一步按这个顺序做

先看本机 `runs/official-evaluation-20261113-stream-low/source-audit-10.md`。它从 36 条原始决策中，以固定种子抽取十条，逐项列出结论、理由、边界和原文。程序已经核对位置与逐字引用，人工需要判断这些原文是否足以支持陈述。

一个待核查例子是“非本服务负责”被转述为“从本需求中移除”，两者是否表示相同范围。另一个例子是理由声称用户否决，但该理由字段只引用 Agent 的提议。这类问题要按原文判断，不能仅凭引用存在就通过。

随后补齐其余阶段的参考，再用相同模型与配置对比 artifact-only、baseline 和 verified。重点看增加复核是否减少误收旧方案、理由无据和范围扩大，同时记录多出的耗时与调用数。所有原始预测保留在各自的新目录中。

完成语义核查与模式对照后，整理运行说明、配置示例和实际评测报告，再判断是否达到题面要求。当前优先用错例改进提示词或提取流程，训练模型不在必要步骤中。
